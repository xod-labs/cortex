# 🚀 Cortex v1.3.1 — Wildly Inaccurate

> *"…though it has many omissions and contains much that is apocryphal, or at least wildly inaccurate, it scores over the older, more pedestrian work in two important respects."* — *The Hitchhiker's Guide to the Galaxy*, on itself.
>
> This is the first patch release to go through the release cycle of 1.3.0, and it is about trusting what is written. GitHub's documentation says a workflow's token cannot write a release whose commit changes a workflow: measured, it can. An issue blamed Microsoft Defender for the slow Windows build: measured, Defender is off on GitHub's runners. `bin/setup-release.sh` guessed which rulesets GitHub applies: now it asks GitHub. Each claim was checked before anything changed. The code changes only where the check found a gap.

## The release cycle

### 🔎 A 404 on a release write says what GitHub documents ([#225](https://github.com/xod-labs/cortex/issues/225))

GitHub's pages *Create a release* and *Update a release* say that `GITHUB_TOKEN` gets a 404 when the release's commit changes a file under `.github/workflows/`, relative to the default branch. That would refuse:
- the draft of a release candidate whose branch changes a workflow, the very case where ADR-009 asks for a candidate;
- the guard's repairs on a release of an older major line.

On 2026-11-03 a throwaway repository replayed the cycle's own calls with `GITHUB_TOKEN`. All of them succeeded, on a commit that changes a workflow as on one that does not:
- the draft;
- a release published at once, so GitHub created its tag;
- the guard's two updates.

**Nothing changes in the cycle.** The release actions now add GitHub's documented reason to the error when one of these calls answers 404, in case GitHub starts enforcing it. A 404 already failed the `draft` job and stopped the guard, with no false verdict. ADR-009 records the measurement.

### 🧭 `setup-release` reads the rules GitHub applies ([#226](https://github.com/xod-labs/cortex/issues/226))

`bin/setup-release.sh` reports any other ruleset that requires checks of the default branch or of a line, since GitHub requires every ruleset's checks. It used to match the rulesets' patterns itself, and its own documentation listed four ways to miss one:
- a pattern's `exclude`;
- a pattern such as `refs/heads/**/*`;
- a second page of rulesets;
- an organisation's rulesets.

It now asks GitHub which rules apply to each branch. That covers all four, and a line not cut yet, such as `0.x`. An organisation's or an enterprise's ruleset is named as such, and a rule that requires no check is left out.

## For contributors

- **`bin/check-english.sh` scans and reports a file whatever its path** ([#227](https://github.com/xod-labs/cortex/issues/227)). git quoted a path that is not ASCII, and the check skipped the file silently. A `|` in a path broke the `sed` that prefixed each hit, and the check passed. It now lists files NUL-separated and prefixes hits with `printf`. `bin/tests/test_check_english.py` runs it in a throwaway repository.
- **`#<issue>` goes before the subject of any commit that delivers an issue**, ADR task or not ([#174](https://github.com/xod-labs/cortex/issues/174)). CONTRIBUTING reserved it for ADR work, while the commits had put it on every issue since 1.1.2. The `commit messages` check is unchanged: the `#<issue>` was optional already.

## Upgrading

Nothing to do for a project: the `cortex` command and the spec behave as in 1.3.0.

1. Install the binary again, if you want this one:

   ```bash
   curl -fsSL https://raw.githubusercontent.com/xod-labs/cortex/main/install.sh | sh     # Linux, macOS
   ```

   ```powershell
   irm https://raw.githubusercontent.com/xod-labs/cortex/main/install.ps1 | iex          # Windows PowerShell
   ```

2. Set `version = "1.3.1"` in `cortex.toml` when your team is ready. A project that stays on 1.3.0 keeps working.
3. Run `cortex sync`.

## Notes

- **ADR-009 is amended** (§9, *After 1.3.0 — found in use*): the measurement of GitHub's documented 404, and `#<issue>` for any issue.
- **The Windows build stays the slowest** ([#229](https://github.com/xod-labs/cortex/issues/229)). On GitHub's hosted runner, Defender's real-time protection is off and both disks are excluded, so excluding paths changed nothing. A launch of the binary costs about 0.6 s on Windows, against 0.2 s on macOS. The cost is PyInstaller unpacking the `--onefile` bundle on each launch, and the replay of the CLI's suite launches it hundreds of times. A user pays it once per command. Running the replay's tests in parallel, every one of them still through the binary, is being measured in #229.
- **The first patch release of the cycle.** It changes the release actions, so its candidate, `1.3.1-rc.1`, was published before its pull request into `main` (ADR-009 §3.7). That candidate's branch also changes a workflow file, so it checked #225 on the full cycle.
