# 🚀 Cortex v1.7.0 — The Restaurant at the End of the Universe

> *"There is a theory which states that if ever anyone discovers exactly what the Universe is for and why it is here, it will instantly disappear and be replaced by something even more bizarre and inexplicable. There is another theory which states that this has already happened."* — *The Restaurant at the End of the Universe*.
>
> A team writes a rule of its own into `CLAUDE.md`, and from then on every fix of the template has to be carried over by hand — or the file stays as it was. This release gives the bootstrap file an end: Cortex's block, which Cortex replaces at every upgrade, then, after the end, the team's part, which Cortex never touches. Write your rules below the line, and upgrade without a second look.

## The bootstrap file: Cortex's block, then yours ([ADR-012](../docs/adr/ADR-012-bootstrap-block.md))

The bootstrap templates move to format 2. Cortex's text now ends on two lines:

```markdown
<!-- Below the next line, this file is yours: `cortex upgrade` and `cortex init --force` keep what you write there. -->
<!-- cortex:bootstrap end -->
```

- **Below the end marker, the file is the team's.** `cortex upgrade` writes Cortex's block again when nobody changed it, and puts the team's part back after it, byte for byte. `cortex init --force` does the same. With an end marker, the block takes the file's line endings and byte order mark, so a file checked out with CRLF stays CRLF.
- **Nothing is written that would lose the team's part.** A file that has one is kept, with a note, when the target writes a bootstrap without an end marker — a move down to a version before 1.7.0. A line break of any number of carriage returns, as a Windows script writing over CRLF leaves it, is one line break to the digest and to the split alike.
- **The digest in the marker covers Cortex's block only.** Text below the end marker no longer counts as a change.
- **A change above the end marker** still keeps the block from following Cortex. `cortex upgrade` says so, and says where the team's rules go.
- **The team's part is empty** in a file Cortex writes: no heading to fill in.

Where a rule goes, now that every kind has a place:

| Rule | Where |
|---|---|
| A developer's, or a machine's — a local tool, a proxy | The tool's user-level instructions (`~/.claude/CLAUDE.md`, …), or the developer's `project-context.md` at the workspace root |
| The team's conventions | `project-context.md`; in a workspace, `agents/project-context.md` |
| What the tool must find in its entry file | Below the end marker |

A file written before 1.7.0 has no end marker. A known tool's file nobody changed becomes format 2 at the next upgrade; a `--tool custom` one only by `cortex upgrade --instructions-file PATH` in its project, never by `--all`. One a team changed is kept, with a note: see *Upgrading*.

## `cortex sync` and a link that leads nowhere ([#310](https://github.com/xod-labs/cortex/issues/310), [#312](https://github.com/xod-labs/cortex/issues/312), [#325](https://github.com/xod-labs/cortex/issues/325))

- **`cortex sync --link --from NEW` replaces a `cortex/` link that leads nowhere**, when the project reads it: naming the checkout's new path says where it should lead. `cortex init --link --from NEW` does the same, before it writes anything. A plain `cortex sync`, a copy or a store sync still refuse it; a live link Cortex did not make is never replaced.
- **One message for a link that leads nowhere**, to a checkout or to a store moved since — `CORTEX_HOME` changed. It no longer calls a store a checkout.

## `cortex upgrade` says what it passed over ([#313](https://github.com/xod-labs/cortex/issues/313), [#326](https://github.com/xod-labs/cortex/issues/326))

- On the pinned version, a bootstrap with no marker that is not that version's file — an older Cortex's, or one a team changed — is said, as it is when the version moves.
- `--commit` no longer ends on *Commit cortex.lock.* after finding the lock as committed already, and the summary of `--all` no longer lists such a project under what to commit.

## The cards ([#311](https://github.com/xod-labs/cortex/issues/311), [#314](https://github.com/xod-labs/cortex/issues/314))

- `testing/component-testing` no longer says that axe on a mounted component catches contrast: jsdom computes no colors. Contrast needs a real browser.
- Six role cards had lost an emoji to a replacement character. It is back, and `repo checks` now refuses a tracked file that holds one.

## Upgrading

1. Update the binary: `cortex self-update`.
2. Move your projects: `cortex upgrade --all --dry-run`, then `cortex upgrade --all` — or `cortex upgrade` in one project. A known tool's bootstrap nobody changed is written again in format 2; a `--tool custom` one, only by `cortex upgrade --instructions-file PATH` in its project — `--all` takes no `--instructions-file`.
3. **A bootstrap file your team changed** is kept, with a note. Run `cortex init --force` once, with the options it was written with — the same `--tool`, `--workspace` in a workspace, `--instructions-file PATH` for `--tool custom`. It writes format 2 and keeps yours as `.bak`: copy your rules from it below the end marker, then delete the `.bak`. A rule of your machine belongs in your tool's user-level instructions instead.
4. Commit `cortex.toml`, `cortex.lock` and the bootstrap files written again — or let `--commit --message MESSAGE` do it.
