# 🚀 Cortex v1.4.0 — You Are Here

> *"…and somewhere in it a tiny little marker, a microscopic dot on a microscopic dot, which says 'You are here.'"* — *The Restaurant at the End of the Universe*, on the Total Perspective Vortex.
>
> This release ships [ADR-010](../docs/adr/ADR-010-lock-and-upgrade.md), and it is about knowing where a project stands. Every merge into `main` has been a release since 1.3.0, so moving a project from one version to the next is now a routine. Until now it was four steps by hand, with nothing to say which agents changed, nor whether the project's overlays still held. A project now commits the exact spec it resolved. One command moves it, and says first what changes. The bootstrap file says which layout and format it was written for. The binary replaces itself, and the assistant keeps the machine in step with what the project pins. And the store can be emptied of versions nobody uses.

## `cortex.lock` — the spec a project resolved ([#247](https://github.com/xod-labs/cortex/issues/247))

```toml
# Written by `cortex sync`: the spec this project resolved. Committed — do not edit (ADR-010 §3.2).
format = 1
version = "1.4.0"
digest = "sha256:…"
```

`cortex sync` and `cortex init` write it beside `cortex.toml`, and you commit it. The digest is one SHA-256 over every file of the version's three trees. It is the same whether the version was downloaded or written from the binary, on any system. A spec in the store whose files differ from the locked ones is put in the store again. If it still differs, sync refuses it: this is not the release the team locked.

`cortex validate` warns when the lock is missing, names another version, or holds another digest. `--strict` fails on those warnings. In CI, sync with `cortex sync --locked`: it never writes the lock, so one missing, or naming another version, fails the job instead of being written where nobody commits it.

```bash
cortex sync --locked && cortex validate --strict     # what CI runs
```

## `cortex upgrade` — one command, said first ([#252](https://github.com/xod-labs/cortex/issues/252))

```bash
cortex upgrade --dry-run     # what would change, nothing changed
cortex upgrade               # to this cortex's own version — or `cortex upgrade 1.4.0`
```

It first lists the agents the new version adds, removes and changes: roles, capabilities, personalities, workflows. Then it checks your overlays against the new version. An overlay whose `Base:` the new version removed stops the upgrade, with nothing changed, unless `--force`. Then it does the switch:
- `version` is written in `cortex.toml`, with your comments kept;
- the project is synced, and `cortex.lock` is rewritten;
- the instructions file is written again, if nobody changed it and the new version's template differs.

A file your team adapted is kept, and the command says how to write it again. Commit `cortex.toml`, `cortex.lock` and the instructions file if it was written; teammates run `cortex sync` after they pull. If anything fails, those files are put back as they were. Run on the version the project already pins, `cortex upgrade` finishes an upgrade cut short.

With no version, it never moves a project down: a project pinned to a version newer than your binary is refused, with the `cortex self-update` that serves it. Name the version to move it down.

## The bootstrap marker ([#243](https://github.com/xod-labs/cortex/issues/243), [#141](https://github.com/xod-labs/cortex/issues/141))

Each instructions file `cortex init` writes now carries, under its title:

```markdown
<!-- cortex:bootstrap layout=single format=1 digest=3f2a9c0e71b4d5a8 -->
<!-- Keep the line above as it is: `cortex init` and `cortex upgrade` read it. -->
```

`cortex init` reads a kept file's layout and format from that line, and no longer from its first line. A workspace bootstrap your team retitled, `# Cortex AI Team — Workspace Mode (Acme)`, is no longer taken for a single project's. The digest is that of the file `cortex init` wrote: while it matches, nobody changed the file, and `cortex upgrade` writes it again whenever the new version's template differs — a rewording too. A file your team adapted no longer matches, and is kept.

## `cortex prune` — the store, tidied ([#258](https://github.com/xod-labs/cortex/issues/258))

```bash
cortex prune ~/code --dry-run
cortex prune ~/code
```

It finds the projects under the directories you give, up to six levels down. It keeps the versions they pin or read, plus the binary's own version and any `--keep`, and removes the others from the store. Nothing on a machine lists its projects, so you say where they are. A project elsewhere gets its version back at its next `cortex sync`, checked against its lock.

## `cortex self-update` — the binary, in one command ([#267](https://github.com/xod-labs/cortex/issues/267))

```bash
cortex self-update             # the latest release
cortex self-update 1.4.0       # a given one — older is a downgrade, said as one
cortex self-update --dry-run   # downloaded, checked and run, nothing replaced
```

It downloads the asset your binary was built for — the x86_64 one on Windows on Arm, as the install script chose — from the release, checks it against the release's `SHA256SUMS` as the install scripts do, and runs it once: only a binary that answers with the version asked for is installed. It then takes the running binary's place, under the name it was installed with. On Windows, which refuses to overwrite a running program but not to rename it, the old binary is renamed aside and removed the next time `cortex` starts. With `CORTEX_RELEASES_URL` set to a mirror, it says so: the binary is then checked against that mirror's `SHA256SUMS`, not against GitHub's.

A project pinned to a version newer than your binary is now refused with the `cortex self-update` command that installs it, not with the install script's. And `cortex upgrade`, with no version, tells you when a release newer than your binary is out; `CORTEX_NO_UPDATE_CHECK=1` keeps it from asking.

## The assistant follows the pin ([#271](https://github.com/xod-labs/cortex/issues/271))

The instructions file used to ask you to run `cortex sync` when the spec was missing, or synced for another version than `cortex.toml`'s — after a pull that moved the project, typically. The assistant now runs it itself, and `cortex self-update` first when the sync says your binary is too old for the project. It runs `cortex-ai` when there is one, and `cortex` once `cortex --version` says it is Cortex — never another program of that name. It says what it runs and why; your tool asks you first if it is set to. It never runs `cortex upgrade` of its own accord: moving the project is the team's decision, made in a commit. Ask it to, and it does, the dry run first.

## Upgrading

Nothing to do for a project: a project of 1.3 keeps working. `cortex validate` adds warnings about `cortex.lock`, never errors, and `--strict` turns them into failures.

1. Install the binary again — the last time with the script: from 1.4.0 on, `cortex self-update` does it:

   ```bash
   curl -fsSL https://raw.githubusercontent.com/xod-labs/cortex/main/install.sh | sh     # Linux, macOS
   ```

   ```powershell
   irm https://raw.githubusercontent.com/xod-labs/cortex/main/install.ps1 | iex          # Windows PowerShell
   ```

2. In each project, `cortex upgrade --dry-run`, then `cortex upgrade`. An instructions file nobody changed gets its marker and digest, and the rules that have the assistant sync on its own. One your team adapted is kept: `cortex init --force` writes it again and keeps yours as `.bak`, and you carry your changes over.
3. Commit `cortex.toml`, `cortex.lock` and the instructions file if it was written again.
