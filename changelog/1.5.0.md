# 🚀 Cortex v1.5.0 — Mind-Bogglingly Big

> *"Space is big. You just won't believe how vastly, hugely, mind-bogglingly big it is."* — *The Hitchhiker's Guide to the Galaxy*.
>
> This release ships [ADR-011](../docs/adr/ADR-011-project-registry.md): a machine now knows its Cortex projects. Until 1.4.0, nothing listed them. `cortex prune` asked where they were, and moving every project to a new release meant one `cortex upgrade` per project, run from each one's root. A machine now keeps the list itself, fills it as you sync, and every maintenance command runs from anywhere. It is also the list the cockpit will show.

## The registry — `~/.cortex/projects.toml` ([#281](https://github.com/xod-labs/cortex/issues/281), [#286](https://github.com/xod-labs/cortex/issues/286))

```toml
# The Cortex projects of this machine (ADR-011). Written by cortex — `cortex project` edits it.
format = 1

[[project]]
name = "acme"
path = "/home/dev/code/acme"
```

The file sits beside the store, in `$CORTEX_HOME`, which is `~/.cortex` by default. It has one entry per project root, the workspace root in workspace mode, with a name and a path and nothing else. What a project pins, and what it reads now, are read from the project each time, so the list never disagrees with a `git pull`.

You do not have to fill it. `cortex init` and `cortex sync` register the project they worked on, and so does `cortex upgrade`, which syncs. The command says it once: *registered as acme — `cortex project list` lists this machine's projects*. If the registry cannot be read or written, you get a warning, never a failed sync. On a CI runner, or for a throwaway project, `CORTEX_NO_REGISTER=1` leaves it alone.

```bash
cortex project list            # each project: its pin, the version read now, its layout, its state
cortex project list --json     # the same, for scripts — and the cockpit
cortex project add [PATH] [--name NAME]
cortex project remove NAME     # drops the entry; the project's files are not touched
cortex project check           # exits 1 on a project gone, or unreadable
```

## `cortex prune` with no directory ([#289](https://github.com/xod-labs/cortex/issues/289))

```bash
cortex prune --dry-run
cortex prune
```

With no `DIR`, the projects are the registry's. It keeps the versions they pin and read, plus the binary's own and any `--keep`, and removes the others. An entry whose project is gone is dropped from the registry, and said. A project moved, or on a drive that is not mounted, gets back on the list at its next sync, and gets back its version too, checked against its lock. `cortex prune DIR...` works as in 1.4.0, and never touches the registry.

## `cortex upgrade --all` ([#292](https://github.com/xod-labs/cortex/issues/292))

```bash
cortex upgrade --all --dry-run
cortex upgrade --all
cortex upgrade --all --branch cortex-1.5.0 --commit --message "chore: Cortex 1.5.0"
```

Every registered project gets the upgrade of 1.4.0, in name order. A project that refuses does not stop the others: its overlays fail, or its sync refuses. The command ends with one line per project, telling which moved, which was already on the target, which refused and which were skipped, and with what each must commit. It exits 1 if a project refused.

Nothing is committed unless you ask. `--branch NAME` makes a branch in each git project before writing. `--commit` commits the files the upgrade wrote, and only those, with the message you give: your team's commit convention is its own. Nothing is pushed. Both options also work without `--all`.

As with `cortex upgrade`, the assistant never runs it of its own accord: moving a project is the team's decision. Ask it to, and it does, the dry run first.

## Upgrading

Nothing to do for a project. The registry fills itself as you sync.

1. Update the binary: `cortex self-update`.
2. Sync each project once, or let your assistant do it. Run `cortex project list` to see what this machine knows.
3. From then on, `cortex upgrade --all` and `cortex prune` work from anywhere.
