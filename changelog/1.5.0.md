# 🚀 Cortex v1.5.0 — Mind-Bogglingly Big

> *"Space is big. Really big. You just won't believe how vastly, hugely, mind-bogglingly big it is."* — *The Hitchhiker's Guide to the Galaxy*.
>
> This release ships [ADR-011](../docs/adr/ADR-011-project-registry.md): a machine now knows its Cortex projects. Until 1.4.0, nothing listed them. `cortex prune` asked where they were, and moving every project to a new release meant one `cortex upgrade` per project, run from each one's root. A machine now keeps the list itself, fills it as you sync, and every maintenance command runs from anywhere. It is also the list the cockpit will show.

## The registry — `~/.cortex/projects.toml` ([#281](https://github.com/xod-labs/cortex/issues/281), [#286](https://github.com/xod-labs/cortex/issues/286))

```toml
# The Cortex projects of this machine (ADR-011). Written by cortex — `cortex project` edits it.
format = 1

[[project]]
name = "acme"
path = "/home/dev/code/acme"
```

The file sits beside the store, in `$CORTEX_HOME`, which is `~/.cortex` by default. It has one entry per project root, the workspace root in workspace mode, with a name and a path and nothing else. What a project pins, and what it reads now, are read from the project each time, so the list never disagrees with a `git pull`.

You do not have to fill it. `cortex init` and `cortex sync` register the project they worked on, and so does `cortex upgrade`, which syncs. The command says it once: *registered as acme — `cortex project list` lists this machine's projects*. If the registry cannot be read or written, you get a warning, never a failed sync. On a CI runner — `cortex sync --locked` registers as any sync does — or for a throwaway project, `CORTEX_NO_REGISTER=1` keeps those three commands from it.

```bash
cortex project list            # each project: its state, its pin, the version read now, its layout
cortex project list --json     # the same, for scripts — and the cockpit: {"format": 1, "projects": [...]}
cortex project add [PATH] [--name NAME]
cortex project remove NAME     # drops the entry; the project's files are not touched
cortex project check           # exits 1 on a project gone, or unreadable
```

A project is `ok`, `missing`, `no-project` — a directory without `cortex.toml` — or `unreadable`, with why. `--json` is the cockpit's contract: its keys only grow within one `format`. `cortex project` exits 2 on a malformed `--name` or a `PATH` that is no directory, and 1 on its other refusals — no `cortex.toml`, a name taken, nothing registered under that key, a registry refused or that cannot be written.

## `cortex prune` with no directory ([#289](https://github.com/xod-labs/cortex/issues/289))

```bash
cortex prune --dry-run
cortex prune
```

With no `DIR`, the projects are the registry's. It keeps the versions they pin and read, plus the binary's own and any `--keep`, and removes the others. An entry whose project is gone is dropped from the registry, and said. A project moved, or on a drive that is not mounted, gets back on the list at its next sync, and gets back its version too, checked against its lock. A directory that lost its `cortex.toml` but kept its `cortex.local.toml` — a branch without Cortex checked out, a rebase under way — stays, with the version it reads. With nothing registered, it exits 2 rather than remove every version. `cortex prune DIR...` works as in 1.4.0, and never touches the registry.

A project whose version is gone — pruned, or a store emptied — is caught by its assistant: the instructions file now has it run `cortex sync` when the directory `spec` names does not exist — and to remove first a `cortex/` that links to a checkout moved or deleted, which the sync refuses ([#303](https://github.com/xod-labs/cortex/issues/303)). `cortex upgrade` to 1.5.0 writes that rule in, unless someone edited the file: it is kept then, with a note, and the rule is yours to copy from the template.

## `cortex upgrade --all` ([#292](https://github.com/xod-labs/cortex/issues/292))

```bash
cortex upgrade --all --dry-run
cortex upgrade --all
cortex upgrade --all --branch cortex-1.5.0 --commit --message "chore: Cortex 1.5.0"
```

Every registered project gets the upgrade `cortex upgrade` has made in one project since 1.4.0, in name order. A project that refuses does not stop the others: its overlays fail, or its sync refuses. The command ends with one line per project, telling which moved, which was already on the target, which refused and which were skipped, and with what each must commit. It exits 1 if a project refused, and 130 when interrupted, its summary said all the same. A `VERSION` it does not serve is refused once, before any project, and the argument errors — `--instructions-file` with `--all`, `--commit` without `--message`, a branch name git refuses — exit 2.

Nothing is committed unless you ask. `--branch NAME` makes a branch in each git project before writing. `--commit` commits the files the upgrade wrote, and only those, with the message you give: your team's commit convention is its own. A project where `cortex.toml` held changes of your own gets no commit, and is said; the lock and the bootstrap files, which the upgrade writes whole, do not count. Fix a project that refused, run the same command again, and the projects done are left as they are, on their branch. Nothing is pushed. Both options also work without `--all`.

As with `cortex upgrade`, the assistant never runs it of its own accord: moving a project is the team's decision. Ask it to, and it does, the dry run first.

## Upgrading

The registry fills itself as you sync — but a project you do not sync before the first `cortex prune` with no directory loses its version: step 2 is for each project, once.

1. Update the binary: `cortex self-update` — from a binary before 1.4.0, the install script, which has no `self-update`.
2. Run `cortex sync`, or `cortex project add`, in each project, before the first `cortex prune` with no directory. Your assistant syncs a project only when its spec is missing or of another version: a project already in step is registered by nobody else, and that first `prune` would remove its version. Run `cortex project list` to see what this machine knows.
3. From then on, `cortex upgrade --all` and `cortex prune` work from anywhere.
