# 🚀 Cortex v1.8.2 — The Whooshing Sound

> *"I love deadlines. I like the whooshing sound they make as they fly by."* — Douglas Adams
>
> 1.8.0 took five review passes over four days, and the deadlines whooshed by. This release sets no deadline: it sets a budget. Every record gets a size, and the size says how many reviews it gets. It also answers the question 1.8.0 made harder to answer: which file pins the version I read?

A documentation release: the `cortex` command and the spec behave as in 1.8.1.

## Every ADR and every release has a size ([#361](https://github.com/xod-labs/cortex/issues/361))

[`docs/process/adr-implementation.md` §10](../docs/process/adr-implementation.md#10-size-and-review-budget) is new:

- **The size.** Five criteria, each scored S, M or L: phases, public surface, the user's files Cortex writes, the environment matrix, the ADRs touched. 5 to 7 is S, 8 to 11 is M, 12 to 15 is L. From ADR-014 on, every record opens with a `Size` section ([the record's structure](../docs/adr/README.md#required-sections)). A release with no ADR is sized in its first pull request. The size is set before the first review and does not move after it.
- **The review budget.** An S record gets 2 review passes, an M 3, an L 4, and each pass gets at most 2 counter-review rounds. There is no fixed duration. A later pass reads the delta only, and an approved phase merges at once.
- **A cap reached is the contributor's call.** Work stops. The contributor who carries the change — a person, never an agent — decides whether there is one more pass, whether the findings become issues, or whether the record is split. Nobody goes past a cap, or splits a record, without that decision. A 🔴 still blocks.
- **What was spent is recorded at closing.** The accepted margin is one pass, or one class. After two records in a row outside it, the thresholds are revisited, and so are the criteria as use shows them wrong.
- **1.8.0's two lessons.** A message that names a command is tested by running that command. A test never pins the version of the binary that replays it.

This is Cortex's own process. Nothing under `agents/` changes: the workflows a host project reads are the same as in 1.8.1. 1.8.2 is the first release sized this way: **S**, two passes.

## Who pins the version? ([#362](https://github.com/xod-labs/cortex/issues/362))

[A new guide](../docs/who-pins-the-version.md) takes the cases one at a time:

- a single project;
- a workspace whose root is no repository, with a team's file;
- a committed `cortex.toml` beside a team's file;
- a teammate who has not synced yet;
- a developer trying a later version;
- CI.

For each one, it says which file wins, which command moves it, and what `cortex config` prints, read line by line. It ends with the locks: why `version` never locks, and why `claude_access` locks to `false` only. Every output in it was printed by `cortex` 1.8.1. The README and Getting Started link to it.

## Upgrading

Nothing to do for a project: the `cortex` command and the spec behave as in 1.8.1.

1. `cortex self-update`, if you want this binary.
2. `cortex upgrade 1.8.2` — or `cortex upgrade --team 1.8.2` for a team's file — when your team is ready. A project that stays on 1.8.1 keeps working.

**A first real try.** A developer's try is read only above a team's version of 1.8.0 or later. No release was above 1.8.1 until this one, so a team on 1.8.1 can now try this release on one machine before moving: run `cortex upgrade --local 1.8.2`.
