# 🚀 Cortex v1.9.0 — The Babel Fish

> *"If you stick a Babel fish in your ear you can instantly understand anything said to you in any form of language."* — *The Hitchhiker's Guide to the Galaxy*
>
> The bootstrap asked each assistant to resolve what the `cortex` command had already resolved: eleven rules to compare versions, tell a checkout from a store, and read where a link leads. This release writes the answer in the block, in plain words, so that every tool reads the same thing the same way. VS Code's Copilot gets the access Claude Code had, and each tool's needs are measured. It closes wave 0.

A minor release: a new format of the bootstrap, a new key, `copilot_access`, and its options. Nothing is removed, and a project that stays on 1.8.x keeps its bootstrap byte for byte.

## The bootstrap says the team's values: format 4 ([ADR-014](../docs/adr/ADR-014-ide-modes.md), [#409](https://github.com/xod-labs/cortex/issues/409))

`cortex init` and `cortex upgrade` now render Cortex's block from the team's resolution. The block names, as text, what the assistant had to work out:

```
<!-- cortex:bootstrap layout=single format=4 digest=… version=1.9.0 theme=h2g2 -->

This project reads **Cortex 1.9.0**, with the theme `h2g2`, and `agents/` is the team's folder …
```

- **The version, the theme, the team's folder, the Prompt Manager's character and the path of its card** are written in the block. The marker carries the version and the theme.
- **The assistant keeps three rules, and one comparison.** It reads `cortex.local.toml` for the spec's path, compares `pinned` in `synced` with the version the block names, and takes a developer's own `theme` over the block's. Format 3 had eleven rules. The rules for a version before 1.8.0, the team's folder compared, and the reading of a `cortex/` link are gone — with the two actions a link to a checkout had ([#378](https://github.com/xod-labs/cortex/issues/378)), and the link's target PowerShell prints otherwise ([#376](https://github.com/xod-labs/cortex/issues/376)).
- **Only the team's values reach the committed block.** A developer's try and theme stay in `cortex.local.toml`. A developer's own bootstrap, one git ignores, is rendered from theirs, and `cortex sync` writes it again when they move, untouched and of format 4.
- **A block behind is said.** When the team changes its theme or its version, `cortex sync` never rewrites the committed bootstrap: it says the block is behind, naming `cortex upgrade` with the team's version. `cortex validate --strict` fails on it, and warns without `--strict`.
- **Each rule is pinned by a table.** Sixteen cases, case → what the assistant runs, hold both templates; the README's table follows them.

## A project on 1.8.x keeps format 3

Format 4's templates ship in the spec of 1.9.0, so a project reads the format of its version. A project pinned to 1.8.x keeps format 3 from its own spec, byte for byte. `cortex upgrade 1.9.0` moves a block of format 3 that nobody changed to format 4. A block the team changed is never rewritten.

## VS Code's Copilot reads the store without asking: `copilot_access` ([ADR-014](../docs/adr/ADR-014-ide-modes.md) §3.5, [#410](https://github.com/xod-labs/cortex/issues/410))

As `claude_access` does for Claude Code:

- **`copilot_access = true`** in `cortex.toml`, for the team — `cortex init --tool copilot --copilot-access`, or the question `cortex init` asks on a terminal — or **`cortex sync --copilot-access`** for you alone.
- **`cortex sync` keeps one entry**, the store's versions folder, in `github.copilot.chat.additionalReadAccessPaths`. It covers every version, so a moved pin changes nothing.
- **The file is VS Code's settings of your machine**: inside a remote — WSL, SSH, a container — `~/.vscode-server/data/Machine/settings.json`, else the user `settings.json` of each VS Code installed. Never the project's `.vscode/settings.json`, which a team commits.
- **Your file is kept.** The edit is a text edit that keeps your comments and the rest of the file. A file it cannot edit that way is left as it is, with a warning naming the line to add.
- **Sync owns its entry, and no other.** `cortex.local.toml` records it as `copilot_entry`, and sync removes it once no project of the machine still sets `copilot_access`. `cortex sync --no-copilot-access` turns it off.
- **A team's file locks it to `false` only**, as `claude_access`: a team may forbid a permission, never grant one on a developer's machine.
- **It does not reach a `link`** — VS Code does not cover a link inside the workspace ([microsoft/vscode#336153](https://github.com/microsoft/vscode/issues/336153)) — **nor Copilot CLI**, which takes `--add-dir ~/.cortex/versions`.

## What each tool needs, measured ([#137](https://github.com/xod-labs/cortex/issues/137))

[Moving to the `cortex` binary](../docs/migrating-to-the-binary.md#7-which-mode-your-tool-needs) gives, for GitHub Copilot, Cursor and Codex, in their IDE and their CLI, whether each reaches the Prompt Manager's card in `store`, `link` and `copy` mode, and what it asks on the way. In short:

| Tool | `store`, the default |
|---|---|
| Claude Code | asks once per session; nothing with `claude_access` |
| GitHub Copilot in VS Code | asks once per session; nothing with `copilot_access` |
| Cursor, Codex | nothing |

Measured again with format 4: Copilot with `copilot_access`, Cursor and the Codex extension reach the card with no prompt to read the store. Cursor, which ran `cortex sync` unasked with format 3 while the versions matched, runs nothing.

## A team's folder that is a junction is named a link, on Windows ([#376](https://github.com/xod-labs/cortex/issues/376))

A team's folder that is a junction leading nowhere was said to be "no folder", with the remedy for a file. It is now said to be a link, and where it leads is written without the `\\?\` Windows puts before a junction's target.

ADR-014 records the decisions, and its amendments what the phases decided and the trials found.

## Upgrading

Everyone runs `cortex self-update` first, then the team moves: `cortex upgrade 1.9.0`, or `cortex upgrade --team 1.9.0` for a team's file. A binary of 1.8.x does not know format 4: a teammate who has not updated is told that their cortex is too old for the project. A project that stays on 1.8.x keeps working, with format 3.
