# 🚀 Cortex v1.8.0 — Life, the Universe and Everything

> *"There is an art, it says, or rather, a knack to flying. The knack lies in learning how to throw yourself at the ground and miss."* — *Life, the Universe and Everything*
>
> A team whose workspace root is no repository could not pin its version: `cortex.toml` was committed nowhere, and every developer moved their own. This release gives the team a file of its own, in its repository, that pins the version for everyone — and lets a developer try a higher one before proposing it. Every setting now says where it comes from.

## The team pins its version ([ADR-013](../docs/adr/ADR-013-configuration-cascade.md))

- **The team's file**, `agents/cortex.team.toml`, committed in the team's repository: `version`, `theme`, `sync`, `claude_access`, and `locked`, the keys it imposes. Its lock, `agents/cortex.team.lock`, sits beside it. One commit there moves every teammate: their assistant syncs after the pull. A team's file that does not read — conflict markers a pull left — is refused, never read as pinning no version.
- **The highest version wins** between the team's and the developer's. `cortex upgrade --local VERSION` writes a try in `cortex.local.toml`, read while it is above the team's, never locked, said at every sync; at or below the team's, it removes it; at or below a developer's own uncommitted `cortex.toml`, read over it, it is refused. During a try the sync leaves the team's lock to `cortex upgrade` at the team's version, which `--locked` and `cortex validate` name with that version — and which only warns where the team's folder cannot be written. A committed `cortex.toml` that pins its own version wins over the team's file.
- **`cortex upgrade --team VERSION`** moves the team's file and its lock, checking the overlays of every project that follows it — at the pin, a lock missing or stale is written — with the file, when it was moved there by hand; `--branch` and `--commit` act in the team's repository, and `--commit` commits nothing where the file holds a change of yours besides its version — or, not committed yet, more than its version — and says so. In a project that follows the team's file — a workspace root that is no repository included — a plain `cortex upgrade X` is refused, naming the commands that work — `--team` to a release this cortex serves, `--local` for a try above the version the project reads — or, when neither does, why. A resume's `--commit` commits nothing where the team's file was moved by hand and not committed. From a 1.8.0 release candidate, a project before 1.8.0 is moved to the candidate first. A bootstrap linked into the team's folder is named where it leads, to commit there.
- **`version` is never lockable**, and **`claude_access` locks to `false` only**: a team may forbid a permission, never grant one on a developer's machine.
- **CI** checks what the team committed: `cortex sync --locked` reads the team's version and lock, never a developer's try.

## Where each setting comes from

- **`cortex config [KEY] [--json] [--locked]`** prints each setting, its value and its origin — the environment, `cortex.local.toml`, `cortex.toml`, the team's file, the machine's file, or the default. `--locked` shows what the team commits.
- **The machine's `~/.cortex/config.toml`** holds `releases_url`, `update_check` and `register`; `CORTEX_RELEASES_URL`, `CORTEX_NO_UPDATE_CHECK` and `CORTEX_NO_REGISTER` still go over it. A key it does not know, a value of the wrong type or a file that cannot be read only warns: `cortex self-update` runs whatever the file holds. A `releases_url` a download would refuse is refused naming the file, by the command that downloads; `cortex config` prints it, with a warning.
- **A version newer than this cortex is said as such**, before any key is checked — no longer as an unknown key a later Cortex added — and before the name of a team's folder this version refuses, which a later one may read.

## The team's folder may be renamed

`agents = "team-agents"`, in a committed `cortex.toml`, renames the team's folder inside the workspace: the cascade's team tier, the team's context files, the overlays `validate` and `upgrade` check, the team's file and its lock, the themes, and what the runtime reads all follow it. Only `agents` itself is the default; a value that leads out of the workspace, names a service, or ends as Windows would read another name — a final dot or space, a `:` — is refused. Names compare composed, in one case a character at a time, composed again: two names a disk keeps apart may be one folder here, never the reverse. A service `Agents/` on a disk that tells case is served, as in 1.7.0. A team's folder that is a symbolic link is read through it. The bootstrap reads the folder `cortex sync` recorded.

## The bootstrap, format 3

The templates move to format 3. `cortex sync` records in `cortex.local.toml` the versions it read (`synced`), and the assistant compares each file's version with it — plain equality: nothing runs when the machine is in step, one sync when a version moved, `cortex self-update` when this cortex is too old — a release candidate or a development build of 1.8.0 is not — each command once, never a loop; when the self-update installed nothing, the assistant says so and stops. A contributor's checkout is left alone. The developer's own bootstrap — one git ignores, or at a root that is no repository — follows the version and theme this machine reads, a try included; the team's committed bootstrap follows the team's version, and one left behind is said.

## The runtime

The runtime reads the team's version through `synced`, and answers `422 — run cortex sync` when a file moved since, when `cortex.toml` names another team's folder than the one recorded, or when a 1.7.0 `cortex.toml` lacks only what the team's file beside it gives — committed, it is said to need it; a valid 1.7.0 `cortex.toml` reads no team's file; a theme the team's file locks wins over `CORTEX_THEME`.

## Development builds ([#342](https://github.com/xod-labs/cortex/issues/342))

A build of Cortex that is no release takes the version it prepares, as a pre-release, read from its branch's CHANGELOG: patching 1.8.0 builds `1.8.1-dev`, a feature `1.9.0-dev`. A source checkout says `X.Y.Z-dev`; the binaries the CI builds say `X.Y.Z-dev.N` — on a pull request into `main` or a line's branch `N.x`, in the merge queue, on a release branch, or run by hand. A pre-release of a version has that version's features. No teammate can download one, so none is written where a teammate reads it: `cortex upgrade --team` refuses to move the team's file to it, and a plain move refuses it into a committed `cortex.toml`; an uncommitted one and a try take it with a warning, as `cortex init` warns when it pins it; a team's file that pins one already keeps it, and its lock. Nothing a run writes for such a version is said to commit: no `commit it` — nor of its lock by `cortex sync --locked` and `cortex validate` — `--commit` commits nothing and `--branch` makes no branch, and the run ends saying so. A refusal names only commands that work — a development version only for a try; from a build that prepares 1.8.0, `--team` only after a self-update to a release that reads the team's file — and, when none does, says why; a release candidate is a release. [CONTRIBUTING](../CONTRIBUTING.md#a-first-change-step-by-step) walks a first change through, from the clone to the pull request whose binaries the reviewer can try.

## Fixes

- `cortex init --force` keeps a workspace's layout without `--workspace` ([#329](https://github.com/xod-labs/cortex/issues/329)), and takes the link it made for its own once `cortex.toml` is gone ([#328](https://github.com/xod-labs/cortex/issues/328)).
- `cortex sync`, `cortex upgrade` and `cortex validate` no longer say to commit at a root that is no repository.
- Git is asked about the project's own repository: a hook's `GIT_DIR` no longer points Cortex's questions at another one, and the configuration its caller gives — a CI's identity, its `safe.directory` — is kept.
- Of another tool's file of the other layout, `cortex init` names `--tool X --force`, which keeps its team's part as `.bak`, never its removal; of a workspace's file `--force` keeps as one, it says how to write a single project's — `cortex init --tool X` once it is removed — and copy the team's part back. Every note that names `cortex init` names the tool: `--force` alone is refused where several instructions files are, and a project left with none writes Copilot's.
- `cortex upgrade` on the pinned version refuses a `cortex/` the sync would refuse before it writes anything, as a move does, and says `cortex sync` puts this machine back only when its sync moved it.
- `cortex init --force` names the backup it wrote, `.bak.1` included, and says git does not ignore it only when git says so; a `.gitignore` read without git is never said to leave a file unignored.
- `cortex validate` of an empty `cortex/` says the version the project needs, as of a spec that is not there.
- The workspace template's step 4.2 lists the services where they are declared.

## Upgrading

1. Update the binary: `cortex self-update`.
2. Move your projects: `cortex upgrade --all --dry-run`, then `cortex upgrade --all` — or `cortex upgrade` in one project. A bootstrap nobody changed is written again in format 3.
3. **To pin the team's version** at a workspace root that is no repository: in the team's repository (`agents/`), write `cortex.team.toml` with `version` and `theme`, run `cortex sync`, and commit the file and `cortex.team.lock`. Announce the move in `agents/project-context.md`; each teammate runs `cortex self-update` once if their cortex is older than 1.8.0, then `cortex sync`, and removes `version` and `theme` from their own `cortex.toml`.
4. Commit `cortex.toml`, `cortex.lock` and the bootstrap files written again — or let `--commit --message MESSAGE` do it.

Nothing changes for a project that adopts none of this: everything new is optional, and a 1.7.0 project reads, syncs and validates as before.
