# 🚀 Cortex v1.10.0 — Resistance Is Useless

> *"Resistance is useless!"* — Prostetnic Vogon Jeltz, *The Hitchhiker's Guide to the Galaxy*
>
> Before the memory comes in, the walls go up: a release is signed, and a mirror can serve one but not change it; what a project's files refer to is checked, a host other than GitHub's is named on every download, a theme change is said once, and the runtime sends the model only the part of the project it needs.

A minor release: a signed `SHA256SUMS` that `cortex self-update` checks, a new warning of `cortex validate`, a new option of the runtime, a note and a refusal. Nothing is removed, and every project keeps working, untouched.

## A release is signed, and `cortex self-update` checks it ([ADR-015](../docs/adr/ADR-015-release-origin.md), [#275](https://github.com/xod-labs/cortex/issues/275))

`SHA256SUMS` proves a download whole, not who built it, and it comes from the host that serves the asset. A mirror named by `CORTEX_RELEASES_URL` could serve a binary with a `SHA256SUMS` that matches it — and the assistant runs `cortex self-update` on its own when the pin asks for it.

- **The release workflow signs `SHA256SUMS`** with an Ed25519 key, in a seventh asset, `SHA256SUMS.sig`. The key is a secret of a GitHub environment that only the release branches reach; a backup key is held offline, and a binary embeds both public keys.
- **`cortex self-update` checks the signature** of a release from 1.10.0 on before it trusts a line of its `SHA256SUMS`, and a release before 1.10.0 against the checksum it embeds for it — whether it comes from GitHub or a mirror. A release unsigned, signed by a key it does not know, or whose `SHA256SUMS` was changed after it was signed is refused, naming what was wrong and the host, and nothing is replaced. There is no option to skip it.
- **The specs were covered already**: a binary embeds the checksum of every spec released before it. **The install scripts do not change**: they trust the host that serves them.
- **A mirror copies the seven assets of a release**, `SHA256SUMS.sig` among them.

## `cortex validate` checks what a project's files refer to ([#140](https://github.com/xod-labs/cortex/issues/140))

A file with no base, a custom addition, was skipped: a workflow that dispatched to a role or a character gone with an old clone passed, and failed at the first conversation that ran it. `cortex validate` now reads every overlay and every custom addition for what it refers to:

- **spec paths** — `cortex/agents/…`, `cortex/docs/…`, `cortex/templates/…` name a file of the spec; `agents/roles/…`, `agents/workflows/…` a file of the spec or of a tier the file reads;
- **roles** — a `roles/{category}/{role}.md` path, or `` `{category}/{role}` `` where a dispatch names it;
- **characters** — an `@Name` tied to a role, `` `role` (@Name) `` or `@Name (role)`, is a character of the team's theme;
- **workflows** named by their path.

Each one that names nothing is a new warning, `REFERENCE_NOT_FOUND`, with its line: `--strict` fails on it, a plain `cortex validate` does not. A mention that is no dispatch is never counted — Claude Code's `@Explore`, a service's `@alias`, an e-mail address, `@types/node` — nor a reference inside a code block or a comment, nor a pattern such as `{service}/agents/…`. [Extending layers](../docs/extending-layers.md) has the table of what counts. ADR-007 records the rule in its amendments.

## A host other than GitHub's is named on every download ([#275](https://github.com/xod-labs/cortex/issues/275))

- **`cortex sync`, `init` and `upgrade` say where a spec comes from** when they download one from a host other than GitHub's releases, as `cortex self-update` does for the binary: once per command, with the setting that named the host — `CORTEX_RELEASES_URL` or the machine's `releases_url`. Nothing is said when nothing is downloaded.
- **A releases URL with a user part — `https://user:pass@host/…` — is refused**, saying why, redirects included. Such a URL never worked: the user part was taken as part of the host. The message never prints the password. The install scripts already refused one.

## `cortex sync` names whom to call when the theme changes ([#397](https://github.com/xod-labs/cortex/issues/397))

Since 1.8.6, `cortex init` ends with the theme's aliases. `cortex sync` now does too when the theme it reads — yours, in `cortex.local.toml`, over the team's — is not the one the last sync read: a teammate's change of theme, or your own, is said once. With no personality, nothing is.

The theme read is recorded in `cortex.local.toml` as a comment, `# synced theme: h2g2`, not as a key: a cortex of 1.9.x, and the runtime of 1.9.x, would refuse a key they do not know. They read the comment past. ADR-013 records it.

## The runtime's project view is an option ([#89](https://github.com/xod-labs/cortex/issues/89))

The project view a run receives — `# Project overview`, `# Workspace services`, `# Project context` — weighs 11,000 to 16,500 tokens on a real workspace. Each part, `overview`, `services` and `context`, can now be kept or left out:

- **for a deployment**, with `CORTEX_PROJECT_VIEW` — the parts separated by commas, or `none`;
- **for a run**, with `project_view` on the request — `/run`, `/resolve`, a manifest endpoint — a list of parts, `[]` for none. It wins over the deployment's.

With neither set, the prompt is byte for byte what it was. An unknown part is refused, naming the accepted ones: `422` on the API, a stop at startup for the deployment's setting. A part left out is not read: leaving out `overview` and `context` keeps the developer's untracked notes away from the model provider. ADR-002 records it.

## Upgrading

`cortex self-update`, then `cortex upgrade 1.10.0`, or `cortex upgrade --team 1.10.0` for a team's file. A project that stays on 1.9.x keeps working. Run `cortex validate --strict` once after the move: a reference that named nothing before now says so.
