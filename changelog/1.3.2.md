# 🚀 Cortex v1.3.2 — Somebody Else's Problem

> *"…it relies on people's natural predisposition not to see anything they don't want to, weren't expecting, or can't explain."* — *Life, the Universe and Everything*, on the Somebody Else's Problem field.
>
> This is the second patch release through the release cycle, and it is about what a check does not see. On the day 1.3.1 shipped, GitHub left a macOS job without a runner four times. It called the job `abandoned`, a result it does not document, and each time the required check passed. One of those times was the merge queue's run of 1.3.1. The checks now list what passes, so they see what they were not expecting. The same afternoon measured why the Windows build is the slowest, and the binary now replays the suite in parallel.

## The release cycle

### 🚦 A required check passes only when every job behind it passed ([#236](https://github.com/xod-labs/cortex/issues/236))

Each workflow that gates a merge ends with one summary job, and the ruleset requires it (ADR-009 §3.10). It failed when a job it needed had failed or was cancelled. GitHub has a third way for a job not to pass: `abandoned`, for a job that no runner took within 15 minutes and that it then cancelled. Its documentation of `needs.<job_id>.result` does not list it.

On 2026-11-03 it happened four times, and each time the summary passed:
- a test job of a pull request into `release/1.3.1`;
- the `builds` check of 1.3.1's pull request into `main`;
- the merge group of that pull request: the merge queue merged 1.3.1 without its macOS build;
- the first release run of 1.3.1. That run stopped before its draft, so nothing was drafted.

Nothing wrong shipped: the same tree had built on macOS twice before.

**A summary now passes when each job it needs passed or was skipped, and fails on anything else**, a result GitHub adds later included. The five workflows share the one condition, and a test runs it. ADR-009 records the change.

### ⏱️ The binary replays the suite in parallel ([#229](https://github.com/xod-labs/cortex/issues/229))

`binary.yml` checks each binary it builds by running the CLI's suite through it, with no Python on its `PATH`. Every test launches the binary, and on Windows each launch unpacks PyInstaller's `--onefile` bundle, about 0.6 s. Run one test after the other, the replay took ten minutes on Windows. Microsoft Defender plays no part: it is off on GitHub's runners.

The replay now goes through `cli/tests/parallel.py`. Twice as many workers as CPUs run the tests at once, the heaviest first. Every test still runs, each one still through the binary.

| Target | The job, before | The job, now |
|---|---|---|
| Windows | 664 s | 324 s |
| macOS | 262 s | 172 s |
| Linux x86_64 | 197 s | 112 s |
| Linux aarch64 | 191 s | 91 s |

Every release, candidate and pull request into `main` waits about 5½ minutes less. A user's `cortex` is unchanged: each command still pays the unpacking once.

## Upgrading

Nothing to do for a project: the `cortex` command and the spec behave as in 1.3.1.

1. Install the binary again, if you want this one:

   ```bash
   curl -fsSL https://raw.githubusercontent.com/xod-labs/cortex/main/install.sh | sh     # Linux, macOS
   ```

   ```powershell
   irm https://raw.githubusercontent.com/xod-labs/cortex/main/install.ps1 | iex          # Windows PowerShell
   ```

2. Set `version = "1.3.2"` in `cortex.toml` when your team is ready. A project that stays on 1.3.1 keeps working.
3. Run `cortex sync`.
